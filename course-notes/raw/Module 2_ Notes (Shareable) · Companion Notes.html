01 · section 01, a loop is just a prompt that fires itself

Section 01, A loop is just a prompt that fires itself

The agent industry sold you a mystery. Peel back the language and the truth is deflating: an agent is a prompt that fires itself. The "loop" everyone reveres is a basic automation concept, a unit of work that re-runs until something tells it to stop. We had cron jobs and event listeners for decades. The only new ingredient is that the thing inside the loop is now a model that can reason about what to do next.

That's good news for you as a PM, because it relocates the hard part. The prompt is trivial to write. The loop around it, when it fires, what counts as done, when it quits, what it carries forward, is where products live or die.

Source. The agent-as-loop framing draws on Claire Vo's discussion of agent loops on the How I AI podcast (2026), and Lenny's Newsletter.

The bridge from Module 1. The agent line told you what to hand over. Loop engineering is how the handed-over work actually runs. You can have a perfect agent-line map and still ship a disaster if the loop never knows when to stop, or wakes up at the wrong time, or forgets what it did last iteration. M1 was the org chart; M2 is the job description.

The model is the worker. The loop is the job.

02 · section 02, onboarding an employee (the mental model)

Section 02, Onboarding an employee (the mental model)

You already know how to design a loop, because you've onboarded a person. When a new hire joins, you don't hand them a single one-off task and walk away. You give them:

  • A recurring responsibility: "own the task queue," not "handle this one task."
  • The tools and access: task queue login, the GitHub/Jira, the posting norms.
  • A definition of done: what a good update looks like, what "approved" means.
  • The judgement to stop or escalate: when to just handle it, and when to come find you.

Designing an agent loop is the same act. Every loop decision maps to an onboarding decision:

Onboarding a hireDesigning a loop
What are they responsible for?Trigger & loop type
What does good work look like?Definition of done
When do they come ask you?Stop / escalate conditions
What do they need access to?Connectors & tools
What do they remember day to day?State

If you wouldn't onboard a human this vaguely, don't ship an agent this vaguely.

03 · section 03, the four loop types

Section 03, The four loop types

Every loop fires for one of four reasons. Naming the trigger correctly is the first real design decision, and it's where most teams overreach.

Loop typeFires when…Cortex exampleWatch for
HeartbeatA continuous check-in cadence: "every N, look at X, act if needed."Every 15 min, scan for status updates that have waited too long.Wasted runs when nothing changed; cost creep.
CronA fixed schedule.9:00am daily task-queue triage sweep.Brittle if the world doesn't fit the clock.
HookAn event triggers it.A new PM task arrives → Cortex drafts an update.Missed/duplicate events; needs idempotency.
GoalRuns until an outcome is validated or it gets stuck, not timer-based."Get this status update to an approvable state," iterating until checks pass.Runaway loops with no stop condition.

The honest default. Most production work is a hook (react to something happening) or a cron (do the sweep on schedule). Heartbeats are hooks for things that can't emit events. Reach for these first.

Goal loops are the powerful, dangerous one. They're the closest thing to "real autonomy," which is exactly why they're the most-often-gotten-wrong. A goal loop has no clock to save it, if you don't define when it's done and when it's stuck, it will spin forever, burn budget, or quietly do the wrong thing with confidence. We come back to this in Section 05.

04 · section 04, the five things every effective loop needs

Section 04, The five things every effective loop needs

Before a loop touches production, it needs five components. These are the difference between a demo loop and a worker. (Map each one to your onboarding model, they're the "give the new hire what they need" list.)

  1. Work trees: an isolated workspace per run. Each iteration gets its own sandbox so a bad run can't corrupt a good one or step on a parallel run. (The "give them their own desk" component.)
  2. Skills: reusable capabilities the loop can call: "draft a status update," "summarise a project's activity." Named, testable units of competence rather than one giant prompt.
  3. Plugins / connectors: the tools and access: the message API, the GitHub/Jira, the data warehouse. This is the agent line made real, exactly what Cortex can reach.
  4. Subagents: delegated sub-tasks and validation. A separate, narrow agent that checks the main loop's work ("does this update match policy?") rather than the loop grading its own homework. (Full depth in Module 3.)
  5. State tracking: what it remembers across iterations: what it's already handled, what it tried, where it is in a multi-step job. Without state, every iteration is amnesiac.

If you can't name all five for your loop, it isn't ready for production, it's a demo.

05 · section 05, context engineering & why goal loops are hardest

Section 05, Context engineering & why goal loops are hardest

Context is the loop's fuel. A loop is only as good as the context you feed each iteration. The model doesn't "remember", you decide, every cycle, what it sees. Four moves (we go deep in Module 4; here's the working vocabulary):

  • Write: record what happened this iteration so the next one can use it.
  • Select: pull in only the context this iteration actually needs.
  • Compress: compaction: summarise long history so it fits the window without losing the thread.
  • Isolate: keep noisy or risky context (e.g. a subagent's scratch work) out of the main loop.

Feed a loop everything and it drowns in tokens and gets dumber; feed it too little and it repeats itself. Context engineering is how you keep each iteration sharp.

Why goal loops are the hardest. A goal loop runs until the outcome is validated or it's stuck, so its design lives entirely in three things a cron or hook gets "for free":

  • Stop conditions: an explicit success condition, a give-up / stuck condition, and an escalate-to-human condition. No clock will rescue a goal loop; you write its exits.
  • Self-validation: how the loop proves it's done rather than just declaring victory. This is the job for a subagent or an eval, not the loop's own optimism.
  • Detecting "stuck": no progress across N iterations, the same action repeating, repeated tool failures. "Stuck" must be a condition you can detect, not a vibe.

This is the natural bridge to Module 5: Bounds & Blast Radius and Evals = the PRD. Your stop conditions and self-validation are where bounds get enforced and where evals become the spec. For now: design the exits before you admire the autonomy.

06 · key takeaways

Key takeaways

01
A loop is just a prompt that fires itself.

The prompt is trivial; the loop, trigger, done, stop, state, is the product. Design the loop, not the prompt.

02
Onboard your agent like an employee.

Recurring responsibility, tools/access, a definition of done, and the judgement to stop or escalate. If you wouldn't onboard a human this vaguely, don't ship an agent this vaguely.

03
Earn the goal loop.

Default to hook or cron; only use a goal loop when you've written its stop conditions and self-validation. Most "autonomy" failures are missing exits.

07 · extra practice (optional)

Extra practice (optional)

  • Take a workflow you own and write its loop type in one sentence: "This fires on ___, is done when ___, and stops when ___." If you can't, you don't understand it yet.
  • For one goal loop you can imagine, write all three stop conditions (success, stuck, escalate) and post them in #cohort-channel.
  • List the five components for a loop you'd actually ship, and flag which one your team always under-invests in.

Glossary

Glossary

TermDefinition
LoopThe recurring unit of work an agent runs. The deflating definition: a prompt that fires itself until a stop condition is met.
TriggerWhat causes an iteration to start, a clock, an event, a continuous check, or an open goal. The first real loop-design decision.
IterationOne pass through the loop: gather context → reason/act → check stop conditions → carry state forward.
Heartbeat loopA loop that runs on a continuous check-in cadence, "every N, look at X and act if needed." Useful when the world can't emit events to react to.
Cron loopA loop scheduled at fixed times (e.g. Cortex's 9:00am daily task-queue triage). Predictable, but brittle if reality doesn't fit the clock.
Hook loopAn event-triggered loop, a new PM task arrives → Cortex drafts an update. The most common production pattern.
Goal loopA loop that runs until an outcome is validated or the agent gets stuck, not timer-based. The most powerful and the most-often-gotten-wrong; requires explicit stop conditions and self-validation.
Definition of doneThe explicit condition that means the work is complete. For goal loops, paired with the validation that actually proves it.
Stop conditionAny rule that ends a loop. Three kinds: success, give-up / stuck, and escalate-to-human.
EscalationThe stop condition where the loop hands control to a human instead of finishing or quitting. The agentic version of "come ask me."
Stuck (detection)A detectable state, no progress across N iterations, the same action repeating, or repeated tool failures, not a vibe. Goal loops must define it explicitly.
Self-validationHow a loop proves it has met its goal rather than just declaring victory, ideally via a subagent or an eval, not the loop grading its own homework.
StateWhat a loop remembers across iterations (what it's handled, what it tried, where it is in a multi-step job) and how long that memory is scoped to persist.
Work treeAn isolated workspace per run, so a bad iteration can't corrupt a good one or collide with a parallel run.
SkillA reusable, named, testable capability a loop can call (e.g. "draft a status update") rather than one monolithic prompt.
Plugin / connectorA tool or system-access integration (message API, GitHub/Jira, data warehouse). The agent line from M1 made concrete.
SubagentA separate, narrow agent that handles a delegated sub-task or validation, e.g. checking the main loop's output against policy. Covered in depth in Module 3.
State trackingThe component that records and reloads state between iterations so the loop isn't amnesiac each cycle.
Context engineeringDeliberately deciding what the model sees each iteration. Four moves: write, select, compress, isolate. The loop's fuel.
Compaction (compress)Summarising long history so it fits the context window without losing the thread.
IsolationKeeping noisy or risky context (e.g. a subagent's scratch work) out of the main loop's context.
Loop SpecThis module's graded repo artifact (02-loop-design/loop-spec.md): trigger & type, definition of done, stop conditions, state, the five components, context plan, and hand-off to bounds/evals. The modernized replacement for the old "AWSpec."
IdempotencyThe property that handling the same trigger twice (e.g. a duplicated task event) doesn't cause duplicate actions. Important for hook loops.
Runaway loopA goal loop with no working stop condition that spins forever, burns budget, or confidently does the wrong thing, the classic goal-loop failure.
