1. Context engineering: the four moves

The agent has no memory. Every loop iteration, you decide what it sees. The agent is only as good as the context that flows into the current iteration.

The unit is the token (~¾ of a word; ~1,000 tokens ≈ 1.5 pages). The context window is the model's working memory, a shared desk that only holds what's on it this turn, rebuilt every loop. Windows are large (≈128K–2M tokens) but not infinite: when the desk fills, oldest items are evicted, mid-window detail is "lost in the middle," and reasoning gets slower, costlier, and worse. This is the distinction behind the name, context is what's on the desk now (ephemeral); memory is what you file away and bring back later (persistent).

MoveWhat it doesFailure if skipped
WritePersist useful context for a future iterationNext iteration starts from zero
SelectPull in only what's relevant this iterationWindow drowns in tokens; model gets dumber
CompressCompact / summarise long history to fit the budgetHistory overflows; the thread is lost
IsolateKeep a sub-task's context out of the main loopOne task's noise poisons another

The failure mode is rarely "not enough context", it's the wrong context crowding out what mattered.

2. Retrieve vs. long-context (the headline decision)

Retrieval *narrows a large/changing corpus to the relevant slice. Long-context *reasons over a bounded set you can just include. Decide per source.

FactorLeans retrieveLeans long-context
Corpus sizeLarge / unboundedBounded, fits the budget
VolatilityChanges often; must be currentStable for the task
Citation / auditMust cite a source passageReasoning over one known doc
CostIncluding it all is wastefulCheap enough to include
LatencyBig payload slows every turnSmall enough not to matter

Naive RAG-by-default is the stale move, not RAG itself.

3. Agentic / hybrid retrieval (not naive RAG)

Naive RAG = embed everything → top-k → stuff the prompt (and answer from junk). Agentic retrieval audits the retriever:

MoveQuestion it answersUse when
RoutingWhich source do I query?Multiple sources, different jobs
Document gradingIs this actually relevant?Top-k returns plausible-but-wrong
RerankingWhat's the best context first?Right passage buried mid-list
Self-verificationDid the answer use the evidence?Citation/audit matters
CachingCan I reuse a prior result?Repeated queries; cost/latency pressure

5. Memory risks & mitigations

RiskWhat goes wrongMitigation
DriftStored facts diverge from realitySource validation; refresh cadence
PoisoningBad input written, then trusted foreverValidate before write; provenance
StalenessWas true, isn't anymoreTTL; re-fetch volatile facts
PII / retentionConfidential or PII data over-stored / over-reachableTTL + scoping (store the minimum)

Memory scope ties back to the Agent Line (M1) and forward to Bounds (M5): TTL, retention, and access scope are bounds you enforce.

Glossary

Glossary

TermDefinition
Context engineeringDeciding, every loop iteration, exactly what the model sees. The model has no memory of its own; the agent is only as good as the context that flows into the current iteration. The four moves: write, select, compress, isolate.
TokenThe unit a model reads and writes text in, roughly ¾ of a word in English (~4 characters). Everything is counted in tokens: instructions, pulled data, and the model's own reply. ~1,000 tokens ≈ 750 words ≈ 1.5 pages.
Context windowThe finite tokens a model can "see" in a single turn, its working memory. Think of a shared desk: only what's on the desk this turn is usable, and it's rebuilt every loop. Windows are large (≈128K–2M tokens across current models) but not infinite.
Context vs. memoryContext is what's in the window this turn, ephemeral. Memory is what persists across loops and is deliberately brought back into the window.
Context budgetThe finite space each loop iteration has for context. Every token spent on history is one not spent on the task, engineering context is spending that budget deliberately.
WriteThe context move of persisting useful context (what happened, a fact, a preference) so a future iteration can use it.
SelectThe context move of pulling in only what's relevant this iteration. The highest-leverage and most-skipped move, more context is not better.
CompressThe context move of compacting or summarizing long history so it fits the budget without losing the thread.
IsolateThe context move of keeping a sub-task's context (e.g. a subagent's scratch work) out of the main loop's window.
Retrieve-vs-long-context decisionThe headline PM call of the module, made per source: narrow a large/changing corpus with retrieval, or reason over a bounded set by just including it.
Retrieval (narrows)Finding the relevant slice of a large, changing, or unbounded corpus so you don't have to include all of it. Its job is to reduce a big thing to a small relevant thing.
Long-context (reasons)Including a bounded, relevant set in full and letting the model reason over all of it, no retrieval machinery, no recall risk.
Naive RAGThe stale 2024 default: embed everything → take top-k by similarity → stuff it into the prompt. Fails quietly by retrieving plausible-but-irrelevant context and answering from it.
Agentic / hybrid retrievalRetrieval the agent reasons about and audits, routing, grading, reranking, self-verification, caching, rather than a blind top-k fetch.
RoutingChoosing which source to query for a given question (e.g. policy KB vs. project records vs. story batch history).
Document gradingChecking whether retrieved chunks are actually relevant and dropping the ones that aren't, before they reach the prompt.
RerankingReordering retrieved candidates so the genuinely best context lands first, even when recall was fine.
Self-verificationChecking whether the generated answer actually used the retrieved evidence, catching confident answers ungrounded in the source.
Caching (retrieval)Reusing prior retrievals or answers instead of re-fetching, for repeated queries under cost or latency pressure.
Working memoryIn-loop scratch context for the current task; discarded after the run.
Episodic memoryA record of what happened in past runs (e.g. a prior decision on a project); scoped per-project and aged out.
Semantic memoryDurable facts and preferences (e.g. a project's roadmap and norms); long-lived and updated deliberately.
Shared memoryContext passed across agents (e.g. a subagent's finding handed to the main loop); scoped to the collaboration.
DriftStored facts quietly diverging from reality over time, making the agent confidently more wrong.
PoisoningBad or adversarial input getting written to memory and then trusted on every future run, contaminating everything downstream.
StalenessMemory that was true and isn't anymore (a a decision was reversed, a norm changed).
TTL (Time-to-Live)An expiration window after which stored data, tokens, or sessions are discarded, the primary mitigation for staleness and retention risk.
Scoping (memory)Storing the minimum data needed and keeping it reachable only by who needs it, the mitigation for PII/retention exposure. Ties to the Agent Line and Bounds.
Team norms (norms doc / PM playbook)The team's PM playbook, the standing rules Cortex must follow (tone, what can be shared, escalation). In the build it's the get_norms source (fixtures/team-norms.md); "norms doc" is shorthand for this playbook.
memory-and-context.mdThe Module 4 repo artifact: context budget, per-source retrieve-vs-long-context table, retrieval quality plan, memory map, and risks & mitigations.
