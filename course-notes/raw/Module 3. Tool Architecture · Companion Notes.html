00 · a note on vocabulary

Nodes, edges, and “graph engineering”

Everything in this module gets discussed elsewhere under a different name. Agents are nodes. Handoffs are edges. What travels along the edges is shared state. Designing that shape deliberately, rather than letting one long chat improvise it, is what the industry currently calls graph engineering. It is the same discipline this module calls orchestration, and the words are worth having, because they are the ones you will meet in tooling docs, job posts, and vendor pitches.

Two distinctions save real confusion:

  • A knowledge graph is not an agent graph. A knowledge graph stores facts and their relationships so something can retrieve them. An agent graph routes work between agents. The overloaded word makes these sound related; they solve unrelated problems.
  • Loops and graphs are not rival camps. A loop is what happens inside a node. A graph is how nodes connect. Much of the “loops versus graphs” argument is a rebrand of the same ideas, prompt engineering, then context engineering, now graph engineering. What actually changed is that a node is now an agent that can misread its brief, which is why definitions of done, bounded state, and deterministic checks matter more than the diagram.

Naming the shape does not make it good. The graph is a drawing until every node has a definition of done and every edge specifies what it passes. The rest of this module is how you earn the drawing.

Reference Card

Frameworks Reference Card

1. The default-to-simple check (run this before you split)

Default to the simplest thing that works. A second agent is a liability you take on deliberately, not a feature you add for free.

Splitting buys you four bills: coordination cost · latency · failure surface · spend. Only split when at least one of these is genuinely true:

Reason to splitWhat it sounds like
Separation of concernsOne job contaminates another (warm update vs. strict posting norms)
ParallelismIndependent sub-tasks can truly run at once, and the time saving beats the overhead
Independent validatorYou want a second set of eyes that didn't write the first draft
Context-window pressureOne agent can't hold everything it needs at once

If you can't name which reason applies, you don't have a multi-agent problem, keep one agent.

2. The three production subagent patterns

PatternHow it worksUse whenCost
DelegationLead spins off a scoped sub-task, gets the result, continuesSub-task is well-bounded / reusableVague delegation → vague results
Critic / validatorSubagent checks output before it proceeds, pass, revise, escalateOutput needs an independent quality gateExtra call; must define "pass"
Parallel fan-out + aggregateSubagents run simultaneously; aggregator mergesIndependent sub-tasks, real time savingRedundancy + conflicts; aggregator is critical

Avoid the exotic (negotiation theatres, deep hierarchies, free-form swarms) until you can measure the benefit.

3. Tool vs. skill vs. subagent (the cost ladder)

What it isUse when
ToolA single call that touches the worldAgent must do one concrete thing outside itself
SkillA reusable capability (instructions + tools + context), defined onceA procedure recurs across agents/loops and you want it consistent
SubagentA whole agent with its own reasoningThe sub-task needs independent judgement or isolation

Prefer a tool → reach for a skill when a procedure repeats → only add a subagent when you genuinely need independent reasoning. Importance isn't the test; need for independent judgement is.

4. The 2026 orchestration landscape (choose on properties, not hype)

OptionGood atReach for it when
OpenAI Agents SDKLightweight agent/tool/hand-off primitivesSimple, code-first wiring without heavy infra
Claude agent SDK / skillsAgent loops with first-class reusable skillsReusable capability + clean skills model matter
LangGraphGraph control over state/flow; observabilityYou need to see and debug the state machine
CrewAIDeclarative roles, low-code feelYou want fast, readable role-based teams
eve (Vercel)Project shape: file-based instructions, tools, approvals, evalsYou want approvals + evals as first-class primitives, plus deploy/observability on one stack
TemporalDurable execution (retries, crashes, long waits)Reliability is the requirement, resumable, exactly-once

*Decide on durability / observability / team fit. The agent frameworks above express logic; Temporal addresses durability: a different axis. Many systems pair the two.*

5. Interop protocols: honest caveats

ProtocolWhat it doesHonest caveat
MCPStandardises agent access to tools/contextUseful for interop; does not by itself make a system governable or safe
A2AStandardises agent-to-agent messaging/coordinationPromising for cross-boundary hand-offs; early, evolving, uneven adoption

Treat MCP/A2A as design considerations, not settled requirements. Name them as optional hand-off mechanisms; don't let your architecture depend on a spec that may shift. A boring, well-logged hand-off you control beats a fashionable protocol you don't.

Golden rule of orchestration: add the part, pay the bill. A clean single agent beats a clever team that collapses. Every agent past the first must justify its existence.

Glossary

Glossary

TermDefinition
OrchestrationThe design of how multiple agents (or an agent and its subagents) are coordinated to complete a goal, who does what, in what order, and how they communicate.
SubagentAn agent invoked by another agent to handle a scoped sub-task, then return its result. Distinct from a tool (a single call) and a skill (a reusable capability).
Multi-agent systemTwo or more agents that coordinate to complete a goal one couldn't, or shouldn't, do alone. A liability you adopt deliberately, not a default.
Default-to-simple checkThe discipline of starting from the simplest design (one agent, maybe a few tools) and only splitting when a specific, nameable reason applies.
Coordination costThe work of routing tasks, passing context, and deciding who does what across agents, logic you must design, debug, and maintain once you split.
Failure surfaceThe total set of ways a system can fail. Each added agent introduces new failure modes: dropped hand-offs, contradictory outputs, stalled waits.
Separation of concernsA reason to split: one job actively contaminates another (e.g. a warm tone vs. strict policy), so they're given to different agents.
Context contaminationWhen mixing conflicting goals or instructions in one agent averages them into output that satisfies neither well.
TopologyThe shape of an agent team: single+subagents, sequential, parallel+aggregate, or hierarchical.
Single + subagentsA topology where one primary agent owns the job and calls subagents for scoped sub-tasks (e.g. Cortex + one validator).
Sequential pipelineA topology where each agent passes its output to the next in a fixed order. Simple, but latency stacks and one bottleneck blocks the line.
Parallel fan-out + aggregateA topology where several subagents work simultaneously and an aggregator merges their results. Needs a strong aggregator and risks redundancy.
Hierarchical teamA topology where a lead agent delegates to worker agents in an org-chart shape. Powerful but adds communication overhead; use sparingly.
DelegationA subagent pattern where a lead agent spins off a well-bounded sub-task to a subagent and continues once it returns.
Critic / validatorA subagent pattern (and role) where a separate agent checks the main agent's output before it proceeds, passing, revising, or escalating it.
Independence (of a validator)The property that makes a validator valuable: it didn't write the draft, so it doesn't inherit the author's blind spots. The author can't grade its own homework.
AggregatorThe component that merges results from parallel subagents into one coherent output. A critical, single point of failure in fan-out designs.
Fail-actionWhat happens when a validator rejects an output: revise, block, escalate to a human, or log. The part most teams hand-wave; specify it concretely.
SkillA reusable capability, instructions + tools + context, defined once and shared across agents and loops. Cheaper than a subagent; more than a single tool.
ToolA single call that touches the world (read a row, send a message, file an approval). The lowest rung on the capability ladder.
Capability ladderThe cost-ordered rule: prefer a tool, reach for a skill when a procedure repeats, and only add a subagent when you need independent reasoning.
Durable executionAn orchestration property (e.g. Temporal) where workflows survive crashes, retry cleanly, and resume after long waits, a reliability axis distinct from agent syntax.
ObservabilityHow easily you can see and debug what agents are doing, state, transitions, hand-offs. A primary criterion for choosing a framework.
MCP (Model Context Protocol)A standard for agents to access tools and context, enabling interop without bespoke glue per integration. Useful, but doesn't by itself make a system governable.
A2A (agent-to-agent)A standard for agents to message and coordinate with each other, including across organisational boundaries. Real and promising, but early and evolving.
