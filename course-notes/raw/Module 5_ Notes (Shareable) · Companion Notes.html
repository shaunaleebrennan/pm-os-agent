01 · section 01, the blast-radius reality

Section 01, The blast-radius reality

For four modules, a mistake cost you a bad demo. Starting now, a mistake costs an incident. That's the whole shift.

Cortex is no longer a thought experiment. It has a connection to the GitHub/Jira, a posting channel that reaches leadership, and a path to posting an update. Real access = real damage. The same capabilities you spent four modules earning are the capabilities that hurt when they misfire.

Walk one bad tool call through Cortex:

  • It drafts an update and posts it to the wrong channel: now confidential roadmap terms are in front of the wrong audience, and you can't recall a post.
  • It pulls the wrong rows and leaks confidential roadmap data into an update.
  • It assembles and commits the team to a story batch on the wrong project, and a scope commitment is the least reversible thing Cortex touches.

This isn't doomerism; it's the 2026 baseline. The public read, loudest on r/artificial, is that we're roughly twelve months from the first major AI agent disaster, precisely because agents now hold Slack, GitHub, Jira, and roadmap access with no confirm button in front of much of it. Builders are already converging on the fix for the worst of it: control for agentic payments starts at infrastructure: ephemeral, just-in-time credentials issued per transaction, not standing write access handed to a loop.

The 2026 PM designs for when it goes sideways, not just the happy path. Every module until now answered "what should Cortex do?" This one answers "what happens when Cortex is wrong, and what stops it from being catastrophically wrong?"

If you can describe what your agent does but not what bounds it, you haven't designed it, you've demoed it.

02 · section 02, bounds & blast radius (the safety spine)

Section 02, Bounds & Blast Radius (the safety spine)

A bound is a hard, enforced limit on the loop, not a polite instruction in the prompt. Prompts are suggestions; bounds are walls. Every agent you ship gets all six, and each one maps to a specific Cortex risk.

BoundWhat it capsCortex risk it contains
Max iterationsLoop runs foreverA reasoning loop spinning on a stuck project thread, burning calls
TimeoutWall-clock runawayA hung tool call freezing the run mid-task
Token / cost budgetSpend per runA loop quietly racking up a four-figure bill overnight
JIT / ephemeral permissionsStanding accessBroad GitHub/Jira + Slack credentials being misused or leaked
Kill switchInability to stop itA misbehaving Cortex you can't halt or roll back fast
HITL checkpointsActing above the linePosting an update / committing to a project without a human

Two of these deserve a closer look.

JIT / ephemeral permissions, "control starts at infrastructure." The instinct is to give Cortex a standing write access and a posting channel and trust the prompt to behave. Don't. Scope access to the moment of need: issue a single-use post authorization for this story batch at this amount that expires on use, rather than handing Cortex standing write access. Same logic for data (read-only, scoped to the project in question) and message (send-on-approval, not standing send). The point: even a fully compromised or confused agent can only do what its current credential allows, and that credential is small and short-lived.

HITL checkpoints are not new, they're the M1 agent line, enforced. Every decision you placed above the line in Module 1 becomes a hard checkpoint here: Cortex does the work, a human approves before it proceeds. Bounds are how the agent line stops being a diagram and becomes a control.

Bounds aren't a tax on a good agent. They're the only reason you can give a good agent real access at all.

03 · section 03, agent failure modes

Section 03, Agent failure modes

Agents fail in ways a single-shot model never could, because they take steps. Six modes show up again and again. For each, you need two things: how you detect it, and the PM lever that contains it.

Failure modeWhat it looks like in CortexHow you detect itPM lever
Tool misuseWrong tool or right tool, wrong args (queries the wrong project)Tool-call logs; tool-call-accuracy evalWhitelist tools; validate args; eval on tool choice
Reasoning loopRe-drafts the same update forever, never convergesIteration counter exceeds maxMax-iterations bound (this is why it exists)
Memory drift / poisoningActs on a stale or planted "fact" from M4 memoryContent eval vs. ground truth; provenance checkTTL + revalidation; trusted-source-only writes
Permission escalationTries an action beyond scope (write to read-only data)403s in logs; permission-denied eventsJIT scoped permissions; alert on denials
Coordination conflictCortex and its validator subagent (M3) disagree / deadlockHandoff-success metric; arbitration logsClear authority; critic gets final say or escalates
OverconfidenceStates a wrong story batch total with full confidenceConfidence-vs-accuracy gap; factual evalRequire uncertainty signal; HITL on low-confidence

A few notes that matter for your spec:

  • Reasoning loops are the reason max-iterations exists. When you can't trust the model to know it's stuck, the bound knows for it.
  • Memory poisoning is drift's nastier cousin: drift is accidental decay; poisoning is a bad value written on purpose or by accident and then trusted. Both are caught the same way: revalidate against ground truth, and don't let untrusted sources write to memory.
  • Most real incidents are compound: a tool misuse triggers a 403, the agent loops on the retry, and overconfidence narrates it as progress. Detect all of them; fix all the root causes, not just the first symptom.
04 · section 04, evals = the prd: trajectory evals

Section 04, Evals = the PRD: trajectory evals

Here's the line worth tattooing on the module: "You spec the agent by writing its evals." In an agentic product, the eval suite is the PRD, it's the precise, testable statement of what "working" means. Ankur Goyal's framing (Braintrust) is exactly right: evals are the modern version of a PRD.

The big shift from the old eval world: don't just grade the final answer, grade the trajectory. A right answer reached through an unsafe or wasteful path is not a pass; it's a near-miss you got lucky on. Four agent-specific dimensions:

DimensionWhat it checksExample pass thresholdOwner
Tool-call accuracyRight tool, right arguments≥ 95% correct tool + valid argsPM + Eng
Path / trajectory qualityNo redundant or unsafe steps on the way≥ 90% clean paths; 0 unsafe stepsPM
RecoveryDoes it recover from a failed step?≥ 80% recover without humanPM + Eng
Task completionDid the goal actually get done?≥ 90% completionPM

The eval lifecycle, where each eval runs:

  1. Offline (fixtures): curated test cases you run on demand while designing. Fast, cheap, deterministic. Your first source of truth.
  2. CI (gate on every change): the offline suite, run automatically on every prompt, tool, or model change. A change that drops a threshold doesn't ship. This is how you avoid silent regressions when you swap models or tweak a prompt.
  3. Production traces (online): real runs, sampled and scored continuously, to catch what fixtures never imagined. Production failures feed back into the offline set.

Cross-link, AI Evals cert. The machinery underneath these dimensions, calibrating an LLM judge, keeping eval families separate so you don't overfit, building per-turn classifiers: is taught in depth in the sister AI Evals certification. Use it. Here we stay agent-specific: the trajectory is our subject.

05 · section 05, replay testing

Section 05, Replay testing

The cheapest high-quality evals you'll ever get are the runs you already did. Replay testing is the discipline: record real runs, turn them into deterministic fixtures, and replay them on every change.

The loop:

  1. Record a real Cortex run, the full trajectory: inputs, tool calls, results, decisions.
  2. Freeze it into a fixture, stub the tool responses so the run is fully deterministic (no live calls, same result every time).
  3. Replay it in CI on every change. If a prompt edit or a model swap changes the trajectory, you see it instantly.

Replay turns "it seemed fine when I tried it" into a regression test. Your scariest production incident, captured once, becomes a fixture that guarantees that exact failure can never ship again. The best fixtures are your worst runs.
