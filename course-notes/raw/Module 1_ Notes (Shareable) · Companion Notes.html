01 · section 01, deflate the hype: what an agent actually is

Section 01, Deflate the hype: what an agent actually is

Let's start by draining the mystique. In 2026, an agent is an LLM running in a loop, with tools, memory, and bounds. That's it. Strip away the marketing and the "agentic" buzzword and you're left with four unglamorous parts:

  • A loop: the model runs, looks at the result, and decides whether to run again. A loop is just a prompt that fires itself. The hype turned this basic automation idea into something mystical; it isn't.
  • Tools: the calls that let it touch the real world: read a database, send a message, file an approval.
  • Memory: what it carries between turns so it isn't starting from zero each time.
  • Bounds: the limits that stop the loop running forever, spending forever, or acting outside its lane.

The reason this matters for you as a PM: when building was hard, the win was shipping the agent at all. Now that building is trivial, shipping isn't the achievement, deciding what the agent is allowed to decide is. The job moved from "can we build it?" to "where's the agent line?"

If your standup is still celebrating that the agent "works," you're a release behind. The real question is what you let it own.

02 · section 02, agent vs. workflow vs. copilot

Section 02, Agent vs. workflow vs. copilot

Three things get lumped together as "AI agents." They are not the same, and the difference is exactly who decides the steps.

  • Workflow: you wrote the steps. Fixed sequence: do A, then B, then C. The model might fill in a blank ("draft this paragraph"), but the path is yours. Deterministic, debuggable, boring, and often the right answer.
  • Copilot: the human is in the driver's seat; the model assists in real time. The person decides and acts; the agent suggests, drafts, autocompletes. Think pair-programming, not autopilot.
  • Agent: the model decides the steps, within bounds. You give it a goal and a toolbox; it chooses the path, the order, and when it's done.

So the agent line is literal: it's the point in a workflow where the model stops being told the steps and starts deciding them. Most real products are a blend, a fixed workflow with one agentic slice in the middle, or a copilot that hands off one bounded task to an agent. Your job isn't to pick a camp; it's to draw the line in the right place.

For Cortex: "pull the project's recent activity from the GitHub/Jira" is a fixed step you can script, that's workflow. "Decide which historical updates are relevant context and draft a fitting response" is the model deciding, that's the agentic slice. "PM reviews and approves before it posts" is the human back in the seat, the human-in-the-loop checkpoint (not a copilot, the agent did the work, the human just approves).

03 · section 03, the agent line framework

Section 03, The Agent Line framework

Here's the framework you'll use for the rest of the course. For every discrete decision, direction, or interaction in a workflow, score it on three axes:

  • Reversibility: if the agent gets this wrong, how easily can we undo it? (Editing a draft = easy. An posted update = hard.)
  • Blast radius: how much damage does a wrong call cause, and how far does it spread before someone catches it? (A typo in an internal note = tiny. A wrong story batch or an update to the wrong project = large.)
  • Measurability: can we reliably tell after the fact whether it was right? (Did the data query return the correct rows = yes. Was the tone of the update "appropriate" = fuzzy.)

The golden rule:

High reversibility + low blast radius + high measurability → below the line (the agent owns it).
Low reversibility, OR high blast radius, OR low measurability → above the line (a human owns it, or you insert a HITL checkpoint).

Note the asymmetry: you need all three green to drop something below the line, but any one red pulls it back above. The line is conservative by design, autonomy is earned per-decision, not granted wholesale.

Worked example, Cortex:

DecisionReversibilityBlast radiusMeasurabilityVerdict
Draft the status updateHigh (edit before it posts)Low (nothing posted yet)High (PM reads it)Below the line: agent owns
Pull recent activity for a projectHigh (read-only)Low (no write)High (rows are checkable)Below the line: agent owns
Post an update company-wideLow (commitment's gone)High (project, cash, trust)High (you can see afterward if it was right)Above the line: any one red is enough

The first two are exactly what you want an agent doing, high volume, low risk, easy to check. The third is exactly what you don't hand over: even though you can measure it after the fact, low reversibility and high blast radius are enough on their own, one red keeps it above the line.

04 · the agent anatomy

Section 04, the agent anatomy

This is the same machine you saw earlier, an LLM in a loop with tools, memory, and bounds, not a new taxonomy to memorize. What matters is which parts make it production-ready:

ComponentWhat it is
ModelThe reasoning engine, pick by capability, swap freely
ToolsCalls that touch the world (read data, send message, file approval)
MemoryWhat carries between turns and sessions
LoopThe thing that fires the prompt again until done
BoundsMax iterations, timeouts, cost budget, permissions, kill switch, contains the blast radius
EvalsThe spec that proves whether it's doing the job

Bounds + evals are the production-ready layer. It's not the model, frontier models are abundant. The teams that struggle under-invested in everything around it. Three principles keep an agent adaptable and safe: (1) model-agnostic, pick by capability and swap freely; (2) swappable tools, add, remove, or change what the agent can touch as the job evolves; (3) build bounds and evals iteratively, not up front. That's where agents misbehave, overspend, and lose trust, so we dedicate whole modules to each: Loop Engineering (M2), Bounds & Blast Radius (M5), Evals = the PRD (M5).

Be model-agnostic. Don't anchor your design to one model name, assume your default fast model handles the routine slices and you escalate to a frontier model only where reasoning quality earns the cost.

05 · section 05, lab: map cortex's agent line

Section 05, Lab: map Cortex's agent line

Time to do the work. In the lab you'll take Cortex's PM workflow, break it into 6 to 8 discrete decisions, score each on reversibility / blast radius / measurability, and draw the agent line across them, marking HITL checkpoints for the borderline calls. Then write a one-sentence justification per decision using the golden rule.

Deliverable: fill 01-agent-line/agent-line-map.md in your forked repo. Full steps and a worked example are in the Module 1 Lab Guide.

Debrief (post in #cohort-channel): share your hardest above vs. below call, the one decision you went back and forth on, and the single axis (reversibility, blast radius, or measurability) that finally settled it.
